## Goal

Ship a public Linux release of sotf and sotf-systemwide that:

- starts and runs usefully on ordinary Intel and AMD x86-64 machines
  down to Apollo Lake Celerons (J3455-class, no AVX), and on ARM64,
  on Ubuntu 24.04+;
- measures and plays with correct channel identity on ALSA and on
  PipeWire, or fails loudly with a named cause — never silently
  remixed, never silent;
- is safe out of the box (systemwide can never route a microphone to
  the speakers, or audio into a null sink, while reporting success);
- is proven by gates that run on Linux, on the shipped artifacts.

Target versions: sotf 0.7.19 (workspace is at 0.7.18), sotf-systemwide
next 0.7.x with its daemon 0.1.x bump, per each repo's changelog rules.

## Success criteria

1. Shipped x86-64 ELFs contain no instruction outside the declared
   baseline (scan gate green) and start under an Intel-class CPU
   model and on real Intel + AMD hardware. On the maintainer's real
   Celeron J3455 (no AVX): the app starts, stereo playback with a
   typical plugin chain runs xrun-free at 512 frames/48 kHz, a 5.1
   measurement completes, and the optimizer's Fast preset completes
   with an ETA that was honest within ~25%.
2. With the reporter's #258 setup reproduced (PipeWire loopback sink,
   `audio.position = [FL FR FC LFE RL RR SL SR]`, 5.1), each SotF
   measurement target delivers energy to exactly its named position
   and nowhere else, verified by automation, not by ear.
3. On a stock Ubuntu/KUbuntu PipeWire install, first launch: no ALSA
   stderr spew, device lists are deduped and honest, the hardware-PCM
   busy case produces a "held by PipeWire — use the PipeWire device"
   message, and a 5.1 measurement completes or aborts with a named,
   actionable error.
4. sotf-systemwide on Linux presents a real virtual sink ("SotF
   Virtual"), captures its monitor, and refuses to start a pipeline
   whose capture endpoint is a physical microphone or whose output
   is a null/discarder device — with an explicit fault state instead.
5. `just dev-driver-all` passes on a display-less Linux machine.
6. RoomEQ: export availability is known before optimization starts;
   routed 5.1 exports to CamillaDSP and PipeWire; optimization
   progress shows true percent, rate, and ETA on a 4-core machine.
7. All seven GitHub issues are closed by the release (or, for #221,
   closed by the scrollbar landing in the pinned toolkit + app), each
   with a comment linking the release that contains the fix.
8. Artifacts install and run in clean containers for every declared
   distro/CPU/glibc combination in the validation matrix below.

## Decisions (defaults taken; flag any you want changed)

D1. **Support floor (confirmed by maintainer): Apollo Lake CPUs and
Ubuntu 24.04+.** "Floor" means the oldest machine we promise the
shipped binary will even start on; below it, the program dies before
`main()` — an illegal instruction, or a loader error like
`GLIBC_2.39 not found`. Two independent floors exist:

- CPU floor: `x86-64-v2` (SSE4.2/POPCNT) — chosen because the target
  old machines are Celeron J3455-class (Apollo Lake/Goldmont and
  later). Goldmont implements the full v2 set but has **no AVX at
  all**, so the rule is: no AVX/AVX2/FMA/BMI instruction may ever be
  emitted into non-dispatched code, and every SIMD kernel needs a
  correct, fast-enough scalar/SSE fallback (runtime probes already
  exist; Phase 2 adds forced-scalar equivalence + perf tests). Newer
  CPUs still get AVX2/FMA speed via that runtime dispatch. The 0.7.17
  accident was compiling with `native` on an AMD builder, which let
  AMD-only SSE4a in.
- Distro floor: **Ubuntu 24.04 and later** (including KUbuntu and
  other flavours), i.e. glibc ≥ 2.39. Build in an `ubuntu:24.04`
  Docker image — which is what actually produced 0.7.17 — and gate
  artifacts at "no `GLIBC_` requirement above 2.39" so a future
  builder upgrade (e.g. to 26.04) cannot silently raise the floor
  and lock out 24.04 users. Ubuntu 22.04, Debian 12 and RHEL 9 are
  explicitly **not** supported; other distros with glibc ≥ 2.39
  (Debian 13, Fedora 40+, Arch) are best-effort via the tarball.

ARM64 unchanged (NEON baseline + runtime checks).

D2. **Both backends are first-class and both must work.** SotF must
work on a PipeWire desktop (the common case) *and* on an ALSA-only
system (no sound server — pro-audio and minimal installs), for
playback, recording and measurement. The support contract per
environment:

- ALSA present (always): direct `hw:`/`plughw:` devices and the
  `default` PCM work; on a PipeWire system that `default` PCM is
  PipeWire's ALSA plugin, which is also how the hardware PCM being
  owned by WirePlumber is handled (Phase 1 guidance).
- PipeWire present: in addition, measurement output to
  virtual/multichannel sinks uses a **native PipeWire backend**
  (direct `pipewire` crate in sotf-capture) that sets
  `audio.position` from the role layout — this is the only way to
  guarantee channel identity there, because neither cpal host can
  express positions (verified in vendored cpal 0.18.2: ALSA
  `init_hw_params` sets no chmap; its PipeWire backend sets
  channels/rate only). Enabling cpal's `pipewire` feature alone does
  **not** fix #258.

Implementation is two steps, both in this release: Step A opens at
sink width and routes by channel role over ALSA (correct on ALSA-only
and for standard layouts through the ALSA plugin); Step B is the
native backend above, selected automatically for PipeWire-class
endpoints. The Phase 2 validation oracle runs in both environments:
PipeWire active, and PipeWire user services masked (ALSA-only).
Systemwide is the one exception to "both": intercepting other apps
needs a virtual sink, which only the sound server can provide, so
systemwide requires PipeWire (or PulseAudio, via pipewire-pulse); on
an ALSA-only box it can capture a user-provided `snd-aloop` endpoint
when explicitly configured (documented, not installer-managed — it
needs a kernel module and root).

D3. **The installer adds the PipeWire virtual sink.** Every install
path provisions the same versioned drop-in
(`10-sotf-virtual-sink.conf`, a null-audio-sink named `SotF Virtual`
with its monitor source), so after installation the sink simply
exists in the user's sound settings:

- `.deb`: installs it to `/usr/share/pipewire/pipewire.conf.d/`
  (system drop-in directory — no user home access needed); removal
  of the package removes it.
- Tarball `install-daemon.sh` and the AppImage (first daemon start,
  idempotent, logged): install it to
  `~/.config/pipewire/pipewire.conf.d/`; `--uninstall` removes it.

After writing the drop-in, the installer/daemon asks PipeWire to
reload (`systemctl --user restart pipewire.service` is suggested to
the user, never forced mid-playback by the .deb postinst) and the
daemon verifies the node appears, faulting with the exact remedy if
it does not. The daemon then discovers `<sink>.monitor` by name and
defaults capture to it. `pw-loopback`-as-subprocess was rejected: a
config-managed node survives daemon restarts, is visible in user
audio tools, and needs no process supervision. The daemon must never
again treat "default input" as system audio.

D4. **Routed PipeWire export is in scope** (#192): mirror the working
CamillaDSP routed renderer into a PipeWire filter-chain graph.
EasyEffects/Wavelet stay refused-but-explained (format limits), with
a labelled lossy option only if trivial; they are not blockers.

D5. **Branch/review flow** follows the repo protocol: one GitLab
issue per phase (linked to the public GitHub issues), short-lived
branches per phase per repo, GitLab MRs, then publication of the
merged result + tags + assets to GitHub with issue updates. This
checkout's remotes are GitHub-only (`origin`) except autoeq's
`gitea`, and `glab` is not installed — Phase 0 includes wiring the
GitLab remotes/CLI before the first branch. Until that lands, work
stays on local branches named `fix/linux-<phase>-<slug>`.

D6. **No new features** beyond what the issues require. Drift
compensation work is limited to (a) defaulting split-device
measurements to timing-chirp stimuli (existing correction path) and
(b) surfacing the existing uncorrected-drift advisory. A general
adaptive-resampler project is out of scope (filed as follow-up).

## Phase 1 — one honest Linux device layer · ~2–3 days

Owner: `sotf-capture/src/devices/` (already shared via sotf-engine),
consumed by player, GPUI/TUI config UI, and the daemon. This phase is
the foundation for #258, #247 and systemwide; it changes enumeration
and selection only, not stream routing.

1. Device identity: key devices by a stable ID (ALSA card PCM name /
   cpal `DeviceId`), not display name. Persisted preferences and
   `SOTF_CAPTURE_DEVICE`/`SOTF_OUTPUT_DEVICE` accept ID first, name
   substring second (logged when ambiguous, picking the ID-sorted
   first). Dedupe PCM aliases per card to one entry per *role*
   (default/plug, direct hw, surround51/71 where they add real
   channels); never merge capability ranges across sibling PCMs
   (remove the merge in `sotf-capture/src/devices/types.rs:253` and
   carry the providing PCM's name with each advertised config).
2. Classify endpoints: physical, server (pipewire/pulse PCMs),
   virtual/monitor, null/discarder. Extend the denylists in
   `sotf-daw/.../cpal_sink/misc.rs` (`is_virtual_output_device_name`)
   and `sotf-systemwide/.../sotf_daemon/misc.rs`
   (`is_safe_output_device_name`) into one shared classifier in
   sotf-capture covering Linux names (`pipewire`, `pulse`,
   `monitor`, `.monitor`, `null`, `Discard all samples`, `dummy`,
   `easyeffects`, `camilladsp`, `SotF Virtual`). Keep classification
   by meaning (role + name + capability signature), failing closed:
   an endpoint that enumerates 1..64 channels and 1..2^32-1 Hz is a
   software PCM, never physical. Unit-test with the exact strings
   captured on this host plus one unlisted synonym variant.
3. Capability honesty: clamp reported sample-rate ranges to
   8 kHz–768 kHz and channel counts to ≤32 for display and
   negotiation; when a PCM enumerates contiguous counts from 1
   (plugin signature), treat only `default_output_config().channels()`
   as a meaningful width and record that fact on the device model
   (`width_is_fictional: bool`) for Phase 2.
4. Busy-device guidance: when a `hw:` open fails with EBUSY and a
   PipeWire/Pulse server PCM exists, the error (and the device
   picker's inline hint) says the device is held by PipeWire and
   names the server PCM to use instead. Reuse
   `actionable_capture_error` wording; add the same mapping on the
   playback side.
5. ALSA stderr: install `snd_lib_error_set_handler` (via the existing
   alsa-sys linkage behind cpal, or a tiny FFI in sotf-capture) before
   first enumeration on Linux, routing messages to `log::debug`.
   Opt-out env `SOTF_ALSA_VERBOSE=1` restores stderr.
6. Daemon `list_devices` switches to the shared layer (today it
   dedupes only the default entry and returned ~60 rows here); IPC
   payload gains `id`, `class`, `channels` (real), breaking nothing
   (additive fields).

Validation: `cargo test -p sotf-capture devices`; `player-cli devices`
and daemon `list_devices` on this host compared line-by-line against
`wpctl status`/`aplay -L` (golden list in the PR description);
startup of `sotf-desktop` and `sotf-daemon` produces zero ALSA stderr
lines; a unit test proves the null PCM classifies as non-physical and
an unknown "Virtual Loopback Sink (PipeWire)" synonym also fails
closed.

## Phase 2 — channel identity for measurement and playback · ~4–6 days

Closes #258, the audio half of #247, and the graph-width bug found by
`dev-driver-tui`. Owners: sotf-capture (measurement I/O), sotf-daw
engine sink (playback width), sotf-host speaker-config types (roles).

Step A — full width + role routing over ALSA:

1. Kill every `target+1` truncation: `CpalPlayback::start`
   (`signal_recorder/playback.rs:219`), `choose_measurement_output_config`
   (`choose.rs:13` — select the sink/default width, not the smallest),
   multi-capture `exact_config` (`multi_capture.rs:103`, `:559`),
   probe path (`types.rs:366`), and the engine matrix width
   (`engine_playback.rs:146` — build the matrix at stream width).
   Width rule: `default_output_config().channels()` when the PCM is
   a plugin (Phase 1 flag), else the negotiated native width that
   covers the layout; always ≥ layout channel count; error via
   existing `check_output_channel` when the target role has no index.
2. Route by role: translate target speaker → stream index through
   `ChannelLayout`/`ChannelRole` (`sotf-host/.../speaker_config/types.rs`)
   using the ALSA default order for the opened width (2: FL FR;
   4: FL FR RL RR; 6: FL FR FC LFE RL RR; 8: FL FR FC LFE RL RR SL SR),
   replacing GUI list-index routing
   (`app-gpui/components/recording/capture/misc.rs:1611`). The same
   table drives the engine's multichannel playback mapping so player
   and measurement agree. Unit tests pin every (width, role) pair.
3. Fix the fictional-width family in the engine graph path: graph
   snapshot expansion must clamp to the stream's negotiated width,
   never to an enumerated max (the 2→64 failure in
   `tui-roomeq-optimize-export-apply`). Add a regression test with a
   fake device advertising 64 channels.
4. `EnginePlayback::check_health`: map manager `Error` state and
   stream-build failures into the recorder's error with the Phase 1
   busy wording, so a dead device can no longer masquerade as a
   finished sweep. Remove the PipeWire early-skip in
   `verify_working_sample_rate` (`devices/is.rs:40`); probe-stream

5. Measurement record/log lines gain: PCM ID, negotiated width,

## Sequencing and parallelism

```text
Phase 0 (0.5d) ──► Phase 1 (2–3d) ──► Phase 2 (4–6d) ──► Phase 3 (3d) ──► Phase 6 RC
                       │                    │
                       └──► Phase 4 (3–4d) ─┴──► Phase 5 (2d) ─────────►┘
```

Phase 4 needs Phase 1's device model only lightly (config UI) and can
overlap Phase 2; Phase 5 is independent until its triage step. One
developer serial: ~15–19 working days. Each phase = one branch + MR
per touched repo, landed in order; no phase waits on the reporter's
hardware except final retest.

## Highest-risk validation

The #258 oracle (Phase 2) — everything else can be unit-proven, but
channel identity is only real when a permuted-position PipeWire sink
receives each sweep on the right port. Step B (native backend) is
mandatory, so the risk is its unknowns: `pipewire` crate threading
model inside the recorder's synchronous traits, and clock/latency
reporting parity with the ALSA path. Budget the top of the Phase 2
range until the oracle passes; if Step B slips, Step A alone must
not ship claiming PipeWire channel guarantees — it ships with the
explicit warning instead (D2 contract downgraded in the release
notes, Step B as the first follow-up).
